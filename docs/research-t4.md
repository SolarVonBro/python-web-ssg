# T4. Модель доставки и безопасность пайплайна

## 1. Способы доставки: учётные данные и последствия компрометации

| Способ | Что нужно для доставки | Объём прав | Последствия компрометации |
|---|---|---|---|
| push в `gh-pages` (peaceiris/actions-gh-pages) | `GITHUB_TOKEN` с `contents: write` или PAT | Запись во **весь репозиторий** (код, ветки, теги, workflow), а не только в сайт | Подмена кода и workflow, публикация вредоносного релиза; сайт — лишь одно из последствий |
| `upload-pages-artifact` + `deploy-pages` | OIDC-токен (`id-token: write`) + `pages: write` на одном job; долгоживущего секрета нет | Только публикация Pages, токен живёт минуты, привязан к окружению `github-pages` | Минимальные: нет секрета, который можно унести; атакующий внутри job может опубликовать только страницы |
| rsync/scp по SSH с deploy-ключом | Приватный ключ в секрете, `known_hosts` | Зависит от настройки сервера: при ограничении `command=`/chroot — только каталог сайта; при обычной учётке — **вся учётная запись** на сервере | Запись на сервер от имени пользователя; бессрочно, пока ключ не отозван; возможна подмена сайта и использование сервера как плацдарма |
| FTP/SFTP | Логин и пароль (FTP — открытым текстом) | Как правило весь домашний каталог аккаунта | Пароль часто совпадает с учёткой хостинга; FTP перехватывается в сети; для SFTP — как для SSH |
| S3 API (Object Storage) | Статический ключ `access_key/secret` | Определяется политикой: при отдельном сервисном аккаунте и роли на один бакет — только бакет | Перезапись/удаление содержимого бакета; при широкой роли — доступ к другим ресурсам облака |

Вывод: наименьший риск у OIDC-публикации (нет хранимого секрета). Для SSH риск
снижается отдельным ключом **только на этот каталог** (`command="rrsync ..."`,
`restrict` в `authorized_keys`), отдельной учётной записью и возможностью быстрого отзыва.

## 2. Вопросы

**Почему секреты недоступны в workflow из `pull_request` из форка?**
Workflow из форка запускается по коду, который прислал внешний автор: он может
изменить сам workflow и добавить `echo $SECRET | curl …`. Поэтому GitHub для
событий `pull_request` из форков не передаёт секреты и даёт `GITHUB_TOKEN`
только на чтение. Событие `pull_request_target` секреты отдаёт, но выполняется в
контексте базовой ветки — его нельзя сочетать с checkout и запуском кода из PR.
В нашем workflow deploy выполняется только для `main` и не для `pull_request`.

**Зачем фиксировать actions по SHA, а не по тегу?**
Тег — подвижная ссылка: владелец (или тот, кто получил доступ к репозиторию
action) может переместить `v4` на другой коммит. SHA коммита неизменяем.
Поэтому в `pages.yml` все actions закреплены по полному SHA с тегом в комментарии
(обновление — через Dependabot).

**Supply-chain-атака через action и последствия для сайта.**
Скомпрометированный action выполняется внутри job с доступом к секретам и токену
(пример — инцидент `tj-actions/changed-files`, март 2025: вредоносный код
печатал секреты в лог; теги были перенаправлены на вредоносный коммит).
Для опубликованного сайта это значит: кража deploy-ключа/токена, внедрение
в собранные страницы скрипта (кража данных посетителей, майнер, редиректы),
подмена файлов для скачивания. Сайт при этом выглядит «легитимно», потому что
публикуется штатным пайплайном. Меры: SHA-пины, минимальные `permissions`,
отдельные job для сборки и деплоя, окружения с approvals, проверка `site/` перед публикацией.

**Как настроить `known_hosts`, не отключая проверку ключа хоста.**
Получить отпечаток хоста один раз по доверенному каналу
(`ssh-keyscan -p PORT host`, затем сверить `ssh-keygen -lf` с отпечатком, который
сообщает администратор) и положить строку в секрет `HELIOS_KNOWN_HOSTS`.
В job записать её в `~/.ssh/known_hosts` и использовать `StrictHostKeyChecking=yes`
(по умолчанию). Не использовать `StrictHostKeyChecking=no` и
`ssh-keyscan` в самом job без сверки — иначе MITM останется незамеченным.

## 3. Работоспособность без внешних CDN

Проверка выполнена в Chrome headless при блокировке любого DNS, кроме
`127.0.0.1` (`--host-resolver-rules="MAP * ~NOTFOUND, EXCLUDE 127.0.0.1"`):
формулы на странице [P3](results.md) отрисовались (в DOM — 2 элемента
`mjx-container`), шрифты и иконки — штатные/inline SVG.

Что сделано для автономности:

- `theme.font: false` — отказ от Google Fonts (системные шрифты);
- MathJax 3.2.2 (`tex-svg.js`, вывод в SVG, без внешних файлов шрифтов) лежит в `docs/javascripts/`;
- иконки Material встроены как inline SVG; поиск — локальный (lunr).

| Ресурс | Вариант с CDN | Локально | Изменение |
|---|---|---|---|
| Шрифты Roboto + Roboto Mono (10 файлов, ttf, верхняя оценка) | ≈ 369 КБ с `fonts.gstatic.com` | 0 (системные) | −369 КБ, −10 запросов |
| MathJax `tex-svg.js` | ≈ 0,66 МБ gzip с CDN (кэш общий между сайтами) | 2,11 МБ raw / 0,68 МБ gzip с нашего сервера | +0,68 МБ к первой загрузке страницы с формулами |
| HTML страницы результатов | 17,1 КБ / 4,4 КБ gzip | то же | 0 |
| CSS+JS темы | 137,6 + 114,1 КБ raw (22,6 + 34,8 КБ gzip) | то же | 0 |

Итого: внешних запросов на странице — 0; вес первой загрузки страницы с формулами
≈ 0,77 МБ gzip, без формул — ≈ 0,09 МБ gzip. Если формул на странице нет,
MathJax можно не подключать (экономия 0,68 МБ).
